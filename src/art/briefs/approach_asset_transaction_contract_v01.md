# Ohio approach asset family — proposed safe transaction v01

**Design proposal only.** No code, runtime assets or existing manifests changed by this document. A new room-specific family is needed so Ohio approach art does not globally replace art used by yard, catwalk, boss and prototype rooms.

## What exists

`engine/world.py` hardcodes `assets/environments/ohio/` and caches `get_env_asset(name)`; ordinary loaded backgrounds are the same sky, fence and dish for every room using that path, with procedural fallback when needed. Its cache is keyed by filename, including cached `None`, and is not a room-specific manifest resolver. New routing, cache keys/lifetime, explicit depth/phase and fallback are needed. `engine/crt_renderer.py` offers native compositing, but it does not by itself implement room art loading or finite coverage. `main.py` calls `recover_before_load(config.ASSETS_DIR)` before asset use; that recovery hook is useful only if new promotions participate in the same transaction/lock protocol.

`tools/build_assets.py` enumerates `ALL_GROUPS` as 11 civilizations plus `mateo`, `bunker`, `review`. Its dry-run therefore says nothing about separately managed `assets/environments/ohio/` or a new environment family. `_group_paths`, source/output validation and renderer are group-specific; **the CLI cannot currently promote an Ohio approach group**. Do not claim it does. `engine/asset_transactions.py` provides `promote_group`, `recover_pending` and `recover_before_load`: it validates safe relative paths/staged files, copies and hash-verifies originals, records absent files and replacement hashes, writes an archive manifest and journal, then replaces files and restores on caught errors; recovery restores originals/removes formerly absent files. The builder wraps it in a nonblocking `fcntl` exclusive directory lock and checks for a pending journal. The low-level `promote_group` does not acquire that lock itself. A journaled group is not a single atomic multi-file filesystem swap; loader/startup coordination and tests matter. Current instructions already disclose no independent backup and unverified non-macOS/power-loss/concurrent-save guarantees. Do not assert those properties have been solved.

`pyproject.toml` declares `video_game = ["assets/**/*", "data/**/*"]` package data and excludes `video_game.art`, planning and tests. That pattern intends to include nested PNG/JSON runtime files but **must be verified in a new clean wheel** with exact members and an installed launch; source art and provenance under `art/` are not runtime package data. Earlier wheel evidence predates these future additions.

## Minimal proposed paths and metadata

- Original artist masters and all generation/cleanup records remain versioned under `src/art/source/`; untouched master, source hash and transforms remain outside runtime package.
- Review-only compositions remain under `_trash/2026-11-13_separation/historical-reviews/art/reviews/visual_upgrade/`; no preview is promoted by path coincidence.
- Proposed runtime family: `src/assets/environments/ohio_approach_v1/manifest.json` and `far_1152x544.png`; later reviewed world layer, if accepted, `world_architecture_1920x576.png`. New paths are deliberately distinct from `assets/environments/ohio/` and other existing families.
- Manifest schema 1 should explicitly identify `room_id: act_01_approach`, `density: 2`, viewport/world dimensions (480×270 and 960×288), per-layer path and SHA-256, pixel dimensions, role and z-order, origin `(0,0)`, parallax `(0.10,0.05)` for far / `(1,1)` for world-fixed, sample/rounding convention, `repeat: false`, opaque/straight-alpha mode, coverage and review state. Far 1152×544 yields source x offset 0–96 for current camera x=0–480; reserve x=192 is hypothetical coverage only. The optional world layer is 1920×576. A path/hash is not visual approval. Asset-family schema and code are not yet implemented.
- After asset review, the orchestrator will coordinate the technical integration assignment under the user’s existing authorization; no new user permission is implied. Route explicitly by actual room ID only after source and manifest validation. Keep the original Ohio assets untouched. A far-only first experiment should declare the exact active background stack (new far and any intentionally retained legacy layers) and avoid accidentally duplicating old reflector/fence; test the result. Missing/invalid optional family should produce a clear diagnostic and a complete legacy background fallback, without a partially mixed/corrupt frame; it must not silently claim the new art loaded. Other rooms continue on existing paths. Decide and document expected failure behavior before implementation.

## Transaction and test plan

1. Preserve a reviewed candidate and verify exact dimensions, alpha, crop coverage, provenance and hash. Before changing **any existing untracked code, manifest or asset**, snapshot it with verified SHA-256 in a new recovery manifest; record files previously absent. Never overwrite artist masters.
2. Add an explicit allowlisted approach group to the existing staged pipeline **or** use a narrow wrapper around the existing transaction primitives with the same asset-root directory lock, pending recovery, path containment and staged validation. This is an implementation choice for technical review; the existing group enumerations and output validators must be extended deliberately, not bypassed by invoking the current CLI with an unrecognized group. Stage all new family files and their manifest as **one group**; validate matching hashes, schema, density, bounds, alpha and absence of unsafe paths before journal/promotion.
3. Make the caller change backward-compatible first, with verified code recovery copies and existing-art fallback when the optional family is absent. Code lives outside `asset_root`, so the file transaction cannot atomically replace caller code and art together. Sequence and test code/family deployment accordingly; an interrupted or rolled-back family must still boot safely. Do not promote while an already-running game is reading assets: startup lock/recovery is not proven to lock a running session for its lifetime.
4. For explicit group promotion, hold the asset-root lock, invoke the appropriate recovery, stage on a compatible filesystem, hash-check every source/output and manifest, and call the journaled group transaction. Archive manifest records original path, whether absent, original and replacement SHA-256 and restoration. On interruption or failure, verify recovery restores all original bytes/removes originally absent outputs; restore code via its separate verified backup if necessary. Keep archive and log, never mass-clean. No global Ohio replacement or unrecorded metadata rewrite.
5. Exercise transaction tests with temporary asset roots and injected failures (after each replacement, pending journal, corrupted archive, invalid/traversal path, missing/invalid family and duplicate writes), lock contention and crash-recovery behavior supported by the host. Prove cache does not return stale/mixed room art after fallback or scene changes. Verify room routing leaves salvage/dish/arena/prototypes unaffected and that actor/tile/HUD/foreground ordering, blink and camera endpoints remain correct. Test no-wrap coverage and y phase at camera boundaries; render original gameplay geometry at native 960 and display 1920.
6. Run the affected renderer/loader/asset tests and the prescribed offline suite, content validator and locked-group dry-run. A dry-run covering the new group must be explicitly implemented; existing 14-group success is not proof. Build a clean wheel, inspect exact new manifest/PNG members and exclusions, then install and launch it from outside the checkout with temporary saves. Record commands, actual outcomes and graphical/audio limitations. Human art/playback, native performance and art-gate review remain separate.
